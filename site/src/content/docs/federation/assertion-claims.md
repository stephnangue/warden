---
title: "Assertion claims"
description: "How Warden shapes and scopes the identity assertion an upstream verifies — profiles, audience, resource, metadata, the user, and lifetime."
---

When an upstream trusts Warden's issuer, it decides *whether* to honor an
[identity assertion](/federation/oidc-issuer/) — and *how narrowly* to scope what it hands
back — by reading the assertion's **claims**. Shaping those claims is how you hold access to
least privilege at the token level: disclose only what a trust policy can read, pin one
assertion to a single resource, and name the user when the agent acts on their behalf.

This page covers the claims Warden puts in a `warden_identity` assertion and the spec keys
that shape them.

:::note[Internal use only]
An identity assertion is an **internal, per-request artifact**. Warden mints it and exchanges
it at the upstream itself — it is **never handed to the agent**. Agents present only their own
identity to Warden and never see, hold, or send a `warden_identity` assertion. The decoded
examples below are here to explain what a *verifier* receives, not something a caller handles.
:::

## Assertion profiles

A spec's **`assertion_profile`** selects the claim shape. Each profile renders only what
its verifier can bind, so nothing crosses the trust boundary that the other side cannot use.

| Profile | Shape | Fits |
|---|---|---|
| `default` | The agent, and — when a user is disclosed — an RFC 8693 delegation token: the user at the top level, the agent in `act`. | Verifiers that read arbitrary claims: a GCP attribute condition, a secrets vault's `jwt` role, Warden's own JWT auth method, a token-exchange authorization server. |
| `minimal` | The registered claims only — `iss`, `sub`, `aud`, `iat`, `nbf`, `exp`, `jti`. | Verifiers that match `iss`/`sub`/`aud` exactly and read nothing else, such as an Entra ID federated identity credential. |
| `aws` | The registered claims, with the role and projected metadata as **AWS session tags**. | AWS STS `AssumeRoleWithWebIdentity`. Only valid on an `aws` source. |

An unset `assertion_profile` means `default` at mint, for every source. A **new** spec that
mints an assertion on an `aws` source is written with `assertion_profile=aws`, and one on an
`azure` source with `minimal`; the value is stored in the spec, so a read shows it. To create
one in the `default` shape instead, set `assertion_profile=default`. Specs stored before
these defaults existed carry no key and keep minting `default`.

Every profile keeps the agent's subject in the same form:

```
wid:<namespaceID>:<mountAccessor>:<principalID>
```

The namespace and mount in it are generated by Warden and cannot be forged by a namespace
admin, so a trust that binds this `sub` alone is still a tenant boundary. A trust written
against it keeps matching when a spec moves between profiles.

Each profile's shape is fixed once released — trusts bind to it. A different shape ships as
a new profile name.

## The `default` profile

Every assertion carries the standard `iss`, `aud`, `iat`, `nbf` (backdated by a small
skew leeway), `exp` and `jti`. `exp` is `iat` plus the assertion lifetime — five minutes by
default, see [Lifetime](#lifetime--assertion_ttl). The rest depends on whether the spec
**discloses a user**.

### The agent alone

With no user disclosed, the top level names the agent:

| Claim | Value |
|---|---|
| `sub` | The agent's composite `wid:…` subject. |
| `warden_role` | The role the agent was admitted under. Empty for a role-less caller, such as a root token. |
| `warden_metadata` | The agent's projected login metadata. Opt-in, see [`assertion_metadata_claims`](#login-metadata--assertion_metadata_claims). |
| `warden_resource` | The single downstream resource. Opt-in or derived, see [below](#pinning-a-resource--warden_resource). |

```json
{
  "iss": "https://warden.example.com",
  "sub": "wid:ns-3f2a1b:auth_jwt_9c1e:agent-checkout-7",
  "aud": "https://vault.example.com",
  "iat": 1755248400,
  "nbf": 1755248370,
  "exp": 1755248700,
  "jti": "a3d9f0c2-8b41-4e77-9f2a-1c6b5e0d4a88",
  "warden_role": "orders-reader",
  "warden_metadata": {
    "team": "payments",
    "env": "prod"
  },
  "warden_resource": "secret/orders/db"
}
```

There is no `warden_namespace` at the agent level: the composite `sub` already carries it.

### An agent acting for a user

When the spec discloses a [user](/concepts/delegation/), the assertion is an **RFC 8693
delegation token**. The top level is the **user**, whose authority is used, and `act` is the
**agent** exercising it:

| Claim | Value |
|---|---|
| `sub` | The user's id, as their IdP asserted it — the value the user auth role's `user_claim` selects, and the same value `{{user.sub}}` templates. |
| `warden_namespace` | The namespace path, such as `team-payments/`. The root namespace renders `root`. |
| `warden_role` | The auth role the user's token was validated under. |
| `warden_metadata` | The user's projected claims, from `assertion_user_claims`, without `sub`. |
| `act` | The agent: its composite `sub`, `iss` (Warden's issuer URL), `warden_role` and `warden_metadata`. |
| `warden_resource` | As above. |

```json
{
  "iss": "https://warden.example.com",
  "sub": "alice@example.com",
  "aud": "https://vault.example.com",
  "iat": 1755248400,
  "nbf": 1755248370,
  "exp": 1755248700,
  "jti": "5b7e2d91-0c4f-4a3e-8d6b-2f9a1c3e7b40",
  "warden_namespace": "team-payments/",
  "warden_role": "employees",
  "warden_metadata": {
    "username": "alice"
  },
  "act": {
    "iss": "https://warden.example.com",
    "sub": "wid:ns-3f2a1b:auth_jwt_9c1e:agent-checkout-7",
    "warden_role": "orders-reader",
    "warden_metadata": {
      "team": "payments"
    }
  },
  "warden_resource": "secret/orders/db"
}
```

:::caution[Bind `warden_namespace` together with `sub`]
A user's raw id is not a tenant boundary: two namespaces can each have an `alice`. A
verifier of a delegation token **must** bind `warden_namespace` beside `sub`. The value is
the namespace path, matched exactly, and no child path can equal `root`. Within a
namespace, a user id is unique only as far as you make it — users validated against
different IdPs need a `user_claim` that is unique across them.
:::

When the user's own token carried a verified `act` chain, that chain is nested under the
agent as **prior actors**, oldest innermost, each layer as the IdP attested it — `sub`, and
`iss` when it had one. Per RFC 8693, a verifier applies access control to the top-level
claims and the current actor (`act`) only; nested actors are informational.

A delegation is refused when the **agent's** own token carries an `act` chain: the token
would name the agent as the current actor and misstate who acts.

### When a user is disclosed

Listing `assertion_user_claims` on the spec is necessary but not enough. Warden discloses the
user only when all three hold:

- the spec lists **`assertion_user_claims`** (comma-separated; `sub` alone is the minimal
  form);
- the assertion fills the **subject** slot. An actor token (`actor_token_source=warden_identity`)
  always names the agent, since the token service builds `act` from its `sub`;
- the source's verifier can bind claims **beyond `iss`, `sub` and `aud`**. AWS STS, Entra ID
  and Alibaba Cloud RAM cannot, so on an `aws`, `azure` or `alicloud` source the user is
  never disclosed: a raw user id in `sub` with no `warden_namespace` bound beside it would
  let any namespace mint that id.

When the user is withheld, the assertion keeps the agent's composite `sub`, and
`assertion_user_claims` still drives `{{user.<claim>}}` request templating. A spec that lists
it and receives no user principal fails closed.

:::note[Who may act for whom is decided by policy]
The profile renders the pair of principals the agent's policy admitted; it does not decide
that this agent may act for this user. Bind the two with a
[CEL condition](/concepts/cel-conditions/#9-bind-the-user-to-the-agent-acting-for-them) on
the agent's policy — for example, the user token's `may_act` claim compared to the agent. Without one, any agent the
policy authorizes may pair with any valid user token.
:::

## The `minimal` profile

`minimal` emits the registered claims and nothing else: `iss`, the agent's composite `sub`,
`aud`, `iat`, `nbf`, `exp`, `jti`. It is for verifiers that match `iss`, `sub` and `aud`
exactly and evaluate no other claim — every `warden_*` claim would only disclose the role,
metadata and user to a party that cannot use them. It is the create-time default for new
Azure federated specs.

An explicit `assertion_resource` (other than `none`) is refused on a `minimal` spec, since
the profile never emits `warden_resource`. `assertion_user_claims` and
`assertion_metadata_claims` are still accepted: they also drive request templating.

## The `aws` profile

An IAM trust policy for a custom OIDC issuer can condition on `sub` and `aud`, and on
**session tags** carried in the `https://aws.amazon.com/tags` claim — nothing else. The
`aws` profile puts what you want to bind there:

```json
{
  "iss": "https://warden.example.com",
  "sub": "wid:ns-3f2a1b:auth_jwt_9c1e:agent-checkout-7",
  "aud": "sts.amazonaws.com",
  "iat": 1755248400,
  "nbf": 1755248370,
  "exp": 1755248700,
  "jti": "a3d9f0c2-8b41-4e77-9f2a-1c6b5e0d4a88",
  "https://aws.amazon.com/tags": {
    "principal_tags": {
      "warden_role": ["orders-reader"],
      "team": ["payments"]
    }
  }
}
```

- The role becomes the `warden_role` session tag, and each key named in
  `assertion_metadata_claims` becomes a tag of the same name. A trust policy conditions on
  each with `aws:RequestTag/<key>`, and the role's permission policies read them as
  `aws:PrincipalTag/<key>` for attribute-based access control.
- No `warden_*` claim is emitted. An explicit `assertion_resource` is refused.
- With no role and no metadata, no tags claim is emitted at all.

:::caution[The trust policy must allow `sts:TagSession`]
AWS refuses a web identity token that carries session tags unless the role's trust policy
allows **`sts:TagSession`** as well as `sts:AssumeRoleWithWebIdentity`:

```json
"Action": ["sts:AssumeRoleWithWebIdentity", "sts:TagSession"]
```

`aws` is the create-time default for new AWS federated specs. Set
`assertion_profile=default` on a spec to mint without tags.
:::

AWS's tag limits apply, and Warden checks them before minting so a bad token is refused
with a reason rather than by STS: at most 50 tags (one is the role, so at most 49 metadata
keys); keys up to 128 characters and values up to 256; letters, numbers, spaces and
`_ . : / = + - @` only; no `aws:` prefix; and keys unique ignoring case. Keys are checked
when the spec is written, values at mint. The subject may be at most 255 characters.

## Audience

The audience (`aud`) is a property of the source's federation trust, so it is usually
set **once on the source** and derived per driver. An explicit spec-level
**`assertion_audience`** takes precedence, and is required whenever no source-derived
fallback exists (for example, a Vault source forces the spec key when its `audience`
is unset).

## Signing

Every assertion is signed by the issuer's private key — which **may be held in an
external KMS** so it never lives in Warden (see [signer configuration](/configuration/signer/)).
**`assertion_algorithm`** selects the signature algorithm — `RS256` (default) or
`ES256`; the issuer keeps a key set per algorithm, so switching is a config change, not
a re-key.

## Lifetime — `assertion_ttl`

An assertion lives for the issuer's `assertion_ttl` (`5m` by default; see
[Runtime settings](/federation/oidc-issuer/#runtime-settings)). A spec may ask for a
**shorter** one with its own **`assertion_ttl`**, as a duration such as `90s` or `2m`.

- It is a request, capped by the issuer: the assertion lives for the shorter of the two. A
  spec can shorten its assertions, never lengthen them.
- It must be at least **`60s`**, the clock skew the issuer tolerates — a shorter assertion
  could be judged expired on arrival.
- When the request exceeds the issuer's lifetime, the spec write still succeeds and its
  response carries a warning under `warnings` saying the lifetime will be capped.

## Pinning a resource — `warden_resource`

A minted assertion can name the **single downstream resource** the spec targets, under
a top-level `warden_resource` claim, so a verifier that checks arbitrary bound claims
can pin one assertion to one resource — least privilege at the token level. Only the
`default` profile emits it.

The value is **auto-derived** from the spec's config (pure config reads — nothing
touches the network):

| Spec | `warden_resource` |
|---|---|
| AWS `secrets_manager` | `aws-secretsmanager:<secret_id>` |
| AWS `sts_assume_role` | `aws-iam:<role_arn>` |
| Azure `bearer_token` | `azure:<resource_uri>` (always emitted — `resource_uri` defaults to `https://management.azure.com/`) |
| GCP `impersonated_access_token` | `gcp-iam:<target_service_account>` |
| GCP `access_token` | `gcp-wif:<workload_identity_provider>` |
| Vault (`hvault`) | an **unprefixed** value per mint method — the `<kv2_mount>/<secret_path>`, `<aws_mount>/<role_name>`, `jwt_role`, etc. |
| Alibaba Cloud `assume_role` | `alicloud-ram:<role_arn>` |
| Kubernetes | an **unprefixed** `<namespace>/<service_account>`; emitted only when the spec sets both |
| `token_exchange` (single RFC 8707 resource) | `oauth-resource:<uri>` |

Override the derived value with **`assertion_resource=<value>`**, or suppress the claim
with **`assertion_resource=none`**. Treat the value as **opaque** — never parse it (a
resource id may itself contain `:`, and Vault values carry no prefix at all).

> Enforcement is verifier-side. AWS, Azure and Alibaba Cloud trust policies bind only on
> `sub`/`aud` (and, for AWS, session tags), which is why their profiles drop the claim; it
> is enforced by a verifier that checks arbitrary bound claims — an external `jwt` auth
> mount on a secrets vault, or Warden's own JWT auth method — configured to trust Warden's
> issuer.

## Login metadata — `assertion_metadata_claims`

Set **`assertion_metadata_claims`** (comma-separated) to project selected
login-derived [token-metadata](/concepts/tokens/) keys into the assertion, so an
upstream trust policy can gate on attributes such as `team` or `env` without minting a
distinct upstream role per value.

It is least-disclosure: only the named keys are included — never the whole metadata map.
In the `default` profile they ride under the agent's nested **`warden_metadata`** claim (in
`act` when a user is disclosed), so they cannot clobber a registered or `warden_*` claim; in
the `aws` profile each becomes a session tag. The set is size-capped (the request fails
closed if exceeded) and folded into the credential-cache key.

## The user — `assertion_user_claims`

When a [user principal](/concepts/delegation/) is present, a `warden_identity` spec may
set **`assertion_user_claims`** to name the user in the assertion — the user's `sub`
plus the allowlisted claims. In the `default` profile, a disclosed user becomes the
token's subject and the agent moves into `act`; see
[An agent acting for a user](#an-agent-acting-for-a-user) and
[When a user is disclosed](#when-a-user-is-disclosed). The agent-plus-user model is
detailed on the [Delegation](/concepts/delegation/) page.

A claim named here that the user's token does not carry **fails the request**: it scopes a
security-sensitive path, so it is never silently skipped.

:::caution[Changed in v0.21.0]
The `default` shape was rewritten once, as an RFC 8693 delegation token. `warden_sub`,
`warden_auth_mount`, the nested `warden_user` claim and the agent-level `warden_namespace`
were removed; the agent's composite `sub` is unchanged. See
[Upgrading from v0.20.0](/upgrade/from-v0-20/#1-the-default-assertion-profile-is-an-rfc-8693-delegation-token).
:::
