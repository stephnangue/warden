The playground is Warden with everything it protects already in place. One command
starts it with its own identity provider and a small bank behind it — an MCP server
and an HTTP API, with balances, withdrawals, and a payment request planted with a
prompt injection. You then drive the bank from the agent you already use, and watch
Warden at work:

- the agent holds only its identity, and Warden brings the bank's credential;
- policy decides which tools the agent sees, then which arguments it may pass;
- the agent acts for a person, and the bank sees who;
- a memo written by a stranger cannot move the money, however the agent reads it;
- every call lands in the audit log;
- the agent finds its own roles, and calls the same bank over plain HTTP;
- and the last scenario puts your own GitHub behind Warden.

**You need** Docker, or the `warden` binary, and an agent: Claude Code, Codex, Cursor,
Gemini CLI, opencode, VS Code, or any client that speaks MCP. The last scenario also
needs a GitHub personal access token; the first eight run entirely on your machine.

## Three terminal tabs

The tour keeps three tabs apart, on purpose:

| Tab | What runs there |
|---|---|
| `Server tab` | Warden itself. |
| `Warden tab` | Every command of the tour. It holds the root token. |
| `Agent's tab` | Your agent, and nothing else, always started from `$HOME/warden-playground`. |

The root token can do anything, including rewriting the policies the tour shows your
agent cannot get past. An agent started in the `Warden tab` would inherit it, so the
agent always starts in a tab of its own.

## 1. Start the playground

<Tabs syncKey="install">
<TabItem label="Docker">

In the `server tab`:

```bash
docker run --rm --name warden-playground -p 127.0.0.1:8400:8400 \
  ghcr.io/stephnangue/warden:latest -dev-playground -dev-root-token=root
```

In the `Warden tab`, set the root token, and give the tab a `warden` command that
runs the CLI inside the container:

```bash
export WARDEN_TOKEN=root
warden() {
  docker exec -i -e WARDEN_ADDR=http://127.0.0.1:8400 -e WARDEN_TOKEN -e WARDEN_OUTPUT=table \
    warden-playground ./warden "$@"
}
```

Nothing is installed on your machine. The function lives in this tab only, which is
where the tour runs every `warden` command.

</TabItem>
<TabItem label="Binary">

Install the binary — macOS and Linux; for Windows see [Binary](/install/binary/#windows):

```bash
curl -sL https://wardengateway.com/install.sh | bash
```

In the `server tab`:

```bash
warden server -dev-playground -dev-root-token=root
```

In the `Warden tab`, set the root token:

```bash
export WARDEN_TOKEN=root
```

</TabItem>
</Tabs>

After the usual dev-server banner, Warden says where the playground's pieces are:

```
==> Playground

  Identity provider:  https://localhost:8410
  Bank (MCP + REST):  https://localhost:8420
  GitHub MCP:         https://api.githubcopilot.com/mcp (needs your PAT)
```

Your agent only ever talks to Warden, on `127.0.0.1:8400`; the identity provider and
the bank sit behind it. If 8400 is taken, publish another port
(`-p 127.0.0.1:9400:8400`, or `-dev-listen-address` for the binary) and change
`WARDEN_ADDR` in the setup below to match. Everything lives in memory, so a restart
starts over, setup included.

## 2. Pick your agent and take the tour

Choose your agent. Its tab holds the whole tour: the setup, then nine scenarios, each
with the commands to run in the `Warden tab`, what to ask your agent, and what to look
for.

## Look inside

In the `Warden tab`, `warden dev audit` reads the playground's audit log, newest first:

```bash
warden dev audit -decision deny
warden dev audit -user alice
warden dev audit -role-name assistant -limit 5
```

`warden dev jwt` mints more agents and people to try the rules with:

```bash
warden dev jwt agent agent-3
warden dev jwt user carol -may-act agent-3 -claims '{"tier": "premium"}'
```

Both are described under [`warden dev`](/cli/dev/).

## Troubleshooting

- **Every call is refused after a restart, or after eight hours.** The identities the
  setup minted are gone or expired. Run the setup again in the `Warden tab`, then the
  scenario you were on.
- **The agent calls servers the tour did not attach, or every call fails with a
  signature error.** The agent was started outside the playground directory and reads
  that directory's servers instead, perhaps ones from an earlier run whose tokens a
  restart voided. Exit it and start it again from the `agent's tab`, with the command
  your agent's tour gives, such as `cd $HOME/warden-playground && claude`.
- **Port 8400 is already in use.** Publish another one, as in step 1.
- **In scenario 8 the agent has no `$AGENT`.** Load the variables in the `agent's tab`
  with `source $HOME/warden-playground/agent.env`, then restart the agent from there.
- **Codex cannot reach Warden in scenario 8.** Restart Codex once the scenario's
  config is written; it reads the network setting at start.
- **Your shell profile exports `WARDEN_TOKEN`.** Run `unset WARDEN_TOKEN` in the
  `agent's tab` before starting the agent.
